Build, Deploy, and Security Scanning Workflows

  • Community of Practice
Last updated on Oct 15, 2026 by cernus76

Most pages in this section describe the content checks that run on your pull request and give you line-by-line feedback. This page is different: it tours the operational workflows that build the site, publish it, and keep the supply chain healthy.

Unlike the content checks, these workflows run mostly in the background. As a contributor you rarely interact with them directly. The build and deployment workflows run after your change is merged or on a schedule, while the security scans run on a schedule and, for CodeQL and the dependency and workflow audits, on your pull request before merge. They become most relevant to you when your change touches dependencies (package.json, the lockfile) or the workflow files themselves. If that is you, read on. If you are only editing or adding reference-architecture content, you can safely skim.

Where these live

All of these workflows are defined in the .github/workflows/ directory of the repository. The descriptions below reflect what those files actually do.

Build and deploy​

Three workflows build the site; two of them also publish it.

WorkflowFileTriggerWhat it does
Build for GitHub Pagesbuild-main.ymlPush to main or devInstalls dependencies and builds the site, then uploads the result as a Pages artifact.
Deploy to Cloudflaredeploy-to-cloudflare.ymlPush to main, or manual runThe production deployment. Builds with backend configuration and exported diagrams, then publishes to Cloudflare Pages.
Deploy to GitHub Pagesdeploy-manual.ymlManual run onlyA manual build and publish to GitHub Pages, useful for fork builds and previews.

Build for GitHub Pages​

Whenever a change lands on main or dev, the build-main.yml workflow runs a clean install (npm ci) and a production build (npm run build) on Node.js 24. If the build succeeds, it uploads the compiled site as a Pages artifact. This workflow only verifies that the site still compiles after a merge; it does not publish anything (publishing is handled by the deploy workflows). That is why a broken internal link (Docusaurus fails the build on those by default) or malformed front matter can fail it.

Deploy to Cloudflare​

The deploy-to-cloudflare.yml workflow is the one that updates the public production site. It runs when a change reaches main, and can also be started manually. Compared with the plain build, it does extra work so the deployed site is complete:

  • fetches contributor details from the GitHub API,
  • exports the Draw.io diagrams to SVG (and caches them to speed up later runs),
  • builds the site with the backend environment configuration, and
  • rewrites Draw.io links to their hashed URLs.

The finished build is then published to Cloudflare Pages. For how diagrams are authored and exported, see the diagramming guide.

Deploy to GitHub Pages (manual)​

The deploy-manual.yml workflow is triggered on demand (workflow_dispatch). It performs the same diagram export and build steps and publishes to GitHub Pages. It is especially useful for fork builds, for example previewing your contribution on your own GitHub Pages site before opening a pull request.

You do not deploy by hand

As a contributor you never need to run these yourself. Merging an approved change is what moves it toward production. The manual deploy exists mainly for maintainers and for fork previews.

Security and supply chain​

These workflows protect the project from vulnerable dependencies and risky workflow changes. Three run automatically; one is manual.

WorkflowFileTriggerPurpose
CodeQLcodeql.ymlPush and PRs to dev, plus a weekly scheduleStatic code scanning for JavaScript/TypeScript and GitHub Actions.
Scorecardscorecard.ymlPush to dev, weekly, and branch-protection changesOpenSSF supply-chain security scoring.
Security Auditsecurity-audit.ymlPRs touching dependencies or workflows, plus weekly and manualAudits npm scripts, runs npm audit, lints workflows, and reviews dependencies.
REUSE compliancereuse-check.ymlManual run onlyChecks license and copyright compliance.

CodeQL​

CodeQL is GitHub's static-analysis engine. The codeql.yml workflow scans the javascript-typescript and actions code on every push and pull request to dev, and again on a weekly schedule. Findings appear in the repository's code-scanning dashboard.

Scorecard​

The scorecard.yml workflow runs the OpenSSF Scorecard, which rates the project against a set of supply-chain security best practices (such as pinned dependencies and branch protection). It runs on pushes to dev, weekly, and whenever a branch-protection rule changes.

Security Audit​

The security-audit.yml workflow is the one most likely to touch your pull request, but only if your change modifies package.json, package-lock.json, or anything under .github/workflows/. It also runs weekly and can be started manually. It bundles several checks:

  • Audit npm scripts: inspects package.json for dangerous lifecycle hooks (such as preinstall, postinstall, prepare) and suspicious command patterns, and flags scripts that pull in and execute code.
  • npm audit: runs npm audit to surface known vulnerabilities in dependencies and uploads the results to the code-scanning dashboard. On a pull request from a fork the dashboard upload is skipped (the token is read-only), but the audit output and job summary still appear.
  • Audit workflows: lints every workflow with actionlint and checks for risky patterns, for example unpinned third-party actions or missing permission blocks.
  • Dependency Review: on pull requests, uses GitHub's dependency-review action to block newly introduced dependencies that carry high-severity vulnerabilities or disallowed (strong copyleft) licenses.
If you add or update a dependency

Expect the Security Audit to run on your pull request. If it reports a high-severity vulnerability or a disallowed license, the dependency-review step will fail and the maintainers will ask you to pick a different package or version. This is normal, and it keeps the project's dependency tree clean.

REUSE compliance​

The reuse-check.yml workflow runs the FSFE REUSE tool, which verifies that every file carries clear license and copyright information. It is a manual check (workflow_dispatch), used to verify compliance on demand rather than on every change.

Scanners target dev, not main

The security scanners (CodeQL and Scorecard) run against the dev branch. The main branch receives only validated content that has already been promoted from dev, so scanning dev is where issues are caught first.
